# Shader precompilation: `victory warm`

This document explains how VItoriaBr caches shaders between runs, how to check that the cache
is working, and what the `victory warm` command adds.

The warmer uses the runtime's GPU capability detection and caches. Compute pipeline
creation does not execute the shader and does not establish gameplay correctness.

---

## 1. The problem

Xbox game shaders arrive compiled for the console GPU (GFX10/RDNA 2). VItoriaBr must
**translate each shader into DXIL** when the game creates a pipeline using it. The **GPU driver**
then compiles the pipeline (PSO).

Both stages are expensive:
- Translating the largest compute shaders takes ~0.4 seconds each.
- Some driver compilations take more than 3 seconds.
- The first 3D world frame requests more than 1,200 new pipelines.

To avoid blocking the game indefinitely, this work runs on separate threads, with a
**12-second shared window per frame and pipeline kind** (`VICTORY_PIPELINE_WAIT_MS`).
Compute and graphics recording threads have separate windows; concurrent waits count
elapsed time once, rather than reserving the whole budget away from other threads.
After the limit, **the draw is
discarded**: the object disappears for that frame. On the first run, this appears as pop-in,
missing objects, and reduced fps.

## 2. What the repository already provided

VItoriaBr maintains two independent persistence layers, plus a pipeline prewarming list:

| Layer | Contents | Location | Code |
|---|---|---|---|
| DXIL translation cache | Each translated `HostShader` (DXIL bytecode + binding metadata) | `cache_dir\shaders` | `crates/victory-gpu/src/shader_cache.rs` |
| D3D12 Pipeline Library | Driver-compiled PSOs (`host-pipelines.bin`) | `cache_dir\pipelines` | `crates/victory-gpu/src/pipeline/library.rs` |
| "Early" list | Keys of pipelines used during the previous run (`early-pipelines.txt`) | `cache_dir\pipelines` | `crates/victory-gpu/src/pipeline/library.rs`, `crates/victory-gpu/src/pipeline/make.rs` |

In practice, **the first run acted as precompilation**: it populated the DXIL translation cache
and PSO Pipeline Library, so the second run found most work already completed.

For offline commands:
- `victory translate` (without `--warm`) translates all discovered shaders but only produces a
  **report**, optionally validating with `--validate` or testing pipeline creation with
  `--pipelines`. It does not write anything to `cache_dir\shaders`.
- `victory translate --warm <file|all>` **does write** to the same `cache_dir\shaders` used by
  the game, through `victory_gpu::shader_cache::warm`. It can warm only shaders identified by
  16-digit hexadecimal hashes in a log file, or all shaders (`all`), with a time limit
  (`VICTORY_WARM_SECONDS=<n>`) and four threads by default (`--jobs N`). Unlike `victory warm`,
  it does not apply `Container::bytes_of` trimming to standalone DXBC containers.

`victory warm` now compiles compute PSOs into the runtime's pipeline library,
following the hardware-neutral preload workflow in
[DexNom/VIctory](https://github.com/DexNom/VIctory/tree/2e01ab4760db91820ef5f9a9f85761f83cd6b5d0).
It preserves the previous run's `early-pipelines.txt`. Graphics PSOs still require
the title's draw state. Custom `[paths].shader_cache_dir` is respected; the PSO
library lives in its sibling `pipelines` directory, just as during normal play.

### The shader cache key (DXIL translations)

An entry in `cache_dir\shaders` is reused only when its key matches exactly. The content-addressed
cache (`victory-pipeline`, converter `"shader.dxil"` v1) computes BLAKE3 over the converter header
and:

```
[translation fingerprint (32 bytes)] + [console shader container bytes]
```

By default, the translation fingerprint (`build()` in `crates/victory-gpu/src/shader_cache.rs`)
does **not** use the `victory.exe` executable hash. It combines the key-version prefix
(`victory shader cache key 2`), the source of `crates/victory-gpu/src/shader_cache.rs` (which defines
entry encoding), and `victory_shader::emit::translation_fingerprint()`
(`crates/victory-shader/src/emit/mod.rs`), which includes:
- The compile-time hash of sources in `crates/victory-shader/src/`
  (`VICTORY_SHADER_SOURCE_HASH`, generated by `crates/victory-shader/build.rs`).
- The build flags `cfg!(feature = "diagnostics")` and `cfg!(debug_assertions)` (`debug` versus
  `release`).
- The runtime values of all `VICTORY_*` variables read by `crates/victory-shader/src/`
  (`VICTORY_SHADER_SWITCHES`, collected by `build.rs`), including switches such as
  `VICTORY_WAVE_WIDE`, `VICTORY_WAVE_DEEP_SKIPS`, `VICTORY_WAVE_OWN_BITS`, `VICTORY_WAVE_LOCAL`,
  `VICTORY_F16_NEAREST`, `VICTORY_FIRST_HALF`, `VICTORY_FIRSTLANE_OWN`, `VICTORY_SHADER_LOOP_LIMIT`,
  `VICTORY_GROUP_SYNC`, and `VICTORY_SHADER_OPT`.
- The resolved values of `loop_limit()`, `group_sync()`, and `shader_opt()`.
- Relevant host GPU capabilities discovered when creating the D3D12 device:
  - The view-heap limit (`view_heap_limit()`, probed by `probe_view_limit()`).
  - The GPU's maximum wave width (`host_max_wave()`, for example 32 on NVIDIA).
    See [section 5](#5-included-fix-gpu-wave-width-in-the-key).

The fingerprint is recalculated on every lookup, preventing translations made before the device
reports its capabilities from being stored under a later key.

**What invalidates or preserves the DXIL translation cache:**
- **Rebuilding `victory.exe` alone does not invalidate the cache.** Changes outside
  `crates/victory-shader/src/` and `crates/victory-gpu/src/shader_cache.rs`, such as HLE, loader,
  or other `victory-gpu` changes, reuse existing DXIL translations as long as build profile/features
  (`debug`/`release` and `diagnostics`), translator-read `VICTORY_*` switches, and relevant GPU
  capabilities (`host_max_wave`, `view_heap_limit`) stay the same.
- **The cache is invalidated** by changes to translator sources (`crates/victory-shader/src/`),
  the format in `shader_cache.rs`, the build mode (`debug_assertions` or `feature = "diagnostics"`),
  any translator-read `VICTORY_*` variable, or relevant host capabilities
  (`host_max_wave` / `view_heap_limit`).
- **`VICTORY_SHADER_CACHE_KEY=exe`** optionally restores the old behavior by adding the executable's
  BLAKE3 hash (`current_exe`) to the key in `build()`. Only with this variable enabled does every
  binary rebuild isolate the entire cache for that executable. If the executable cannot be read,
  VItoriaBr logs a warning and falls back to the translator-based key.

### How the PSO Pipeline Library differs

The `cache_dir\pipelines\host-pipelines.bin` layer is separate from the DXIL cache. It stores PSOs
already compiled by the D3D12 driver, identified in `library::name()` by a hash of the host
description: pipeline type, serialized root signature, translated shader bytes, and graphics state.
Rebuilding the executable without changing translated DXIL, root signature, or pipeline state
does not invalidate `host-pipelines.bin` either. A driver update or adapter change causes D3D12 to
reject the entire library, whereas translator or graphics-state changes rebuild only PSOs whose
descriptions changed.

## 3. What `victory warm` does

```powershell
.\target\release\victory.exe warm <game_dir>
```

Without arguments, it uses `game_dir` and `test_titles` from `victory.toml`. Options:
- `--list`: prints each shader that cannot be translated.
- `--jobs N`: sets the worker count (defaults to at most four, to bound compiler memory pressure).
- `--no-pipelines`: retains the previous translation-only behaviour.

The command:

1. Uses the **same cache directory** as a normal run (`cache_dir\shaders`).
2. Scans game files using the same search as `victory translate`: standalone DXBC containers
   and SGD5 records.
3. Trims each container to the size declared in its own header (`Container::bytes_of`). These
   are the bytes the game supplies when creating a pipeline. Without trimming, the key would
   include the rest of the file and would never match the game's key.
4. Skips duplicate containers.
5. Calls `victory_gpu::shader_cache::warm` for each container, which:
   - **Creates the D3D12 device first**, just as a normal run does. This sets the view limit
     and wave width, both of which affect translation and the key.
   - Translates and stores through the same `cached` path used by a normal run.
6. Compiles compute pipelines through the runtime's normal PSO/library path and saves
   the library. It does not dispatch any shader. Graphics shaders only warm translations.
7. Prints translation and compute-pipeline counts separately. Empty scans or scans
   with no successful translations are errors; partial refusal is reported explicitly:

```
shader cache D:\victory-data\cache\shaders
containers   25758 distinct: 25629 translated now, 0 already cached, 129 do not translate (412.3 s)
warm         25629 translated, 129 refused; 12000 compute pipelines, 30 refused; 412.3 s
     ...     <reason>  (e.g. <file>@<offset>)
```

On the second run, keeping the translator, build mode (`release`/`debug` and `diagnostics`),
relevant host capabilities, and translator-read `VICTORY_*` variables unchanged (or using the same
executable when `VICTORY_SHADER_CACHE_KEY=exe` is set), almost everything should be reported as
`already cached`.

> These numbers are illustrative. Actual results depend on your machine.

### Golden rule

**Run `warm` with the same translator, build profile/features (`release` versus `debug`, with or
without `diagnostics`), GPU (`host_max_wave` and `view_heap_limit`), and translator-read
`VICTORY_*` variables that you will use to play.**

- A `diagnostics` or `debug` build uses a different cache not because it is another `.exe`,
  but because `cfg!(feature = "diagnostics")` and `cfg!(debug_assertions)` are part of the
  translator fingerprint.
- Changed code outside `crates/victory-shader/src/` and `crates/victory-gpu/src/shader_cache.rs`,
  then rebuilt with the same profile/features? **You do not need to run `warm` again**:
  the DXIL translations remain valid.
- Rewarming is needed only after changes to the translator (`crates/victory-shader/src/`),
  `shader_cache.rs`, build profile/features, any translator-read `VICTORY_*` switch, a change to
  a GPU with different wave/view limits, or when using `VICTORY_SHADER_CACHE_KEY=exe` (in which case
  each new executable requires its own cache).

## 4. What `victory warm` does NOT cover

`victory warm` covers the DXIL translation cache and compute PSOs for containers
found in game files. It does not invent graphics state or add entries to the
title's prewarm list; it preserves entries recorded by earlier gameplay runs.

| Case | Reason | Outcome |
|---|---|---|
| Shaders generated or loaded only in memory | Not present in files | Still translated during gameplay |
| Graphics PSO compilation | Depends on graphics state (formats, blend, layout) supplied only by the game | Still happens during play; subsequently stored in the Pipeline Library (`host-pipelines.bin`) and `early-pipelines.txt` list |
| Unsupported wave64 operations on a wave32 GPU | Warming cannot supply missing translation support | Reported as refused; no AMD/native-wave64 assumptions are imported |
| A game supplies a `size` different from the container size | The key changes | Cache miss: the shader is translated normally, without an error |
| Driver or GPU change | The Pipeline Library rejects the old library | PSOs are recompiled; the DXIL translation cache remains valid if `host_max_wave` and `view_heap_limit` match |

In short, `warm` moves translation and compute-driver compilation ahead of play.
Graphics-driver compilation remains dependent on encountered draw state.

For an explicit wave32 target, set `VICTORY_HOST_WAVE = "32"` under
`[environment]` in `victory.toml`. This cap applies to warming and gameplay
and never raises the physical GPU's maximum. Wave64 compute kernels still
need correct cross-half emulation; the translator refuses a result that
still requires wave64 instead of submitting it to a wave32 device. It does
not strip `WaveSize(64)`, change thread-group sizes, or enable experimental
wave widening. Such a refusal is an unresolved compatibility gap, not a
successful warm-up or a guarantee of complete rendering.

D3D12 message 971 (`Load*Pipeline`: no pipeline stored with this name) is
an expected library miss before normal pipeline creation. It is separate
from an unsupported shader wave width or a failed PSO.

## 5. Included fix: GPU wave width in the key

Translation depends on the GPU: on cards with at most 32 lanes per wave (NVIDIA), wave64 programs
are translated differently (`set_host_max_wave`, called when creating the device). This value
**was missing from the cache fingerprint**. Switching from an AMD card to NVIDIA, or vice versa,
could reuse translations made for the other card.

In the current code, `build()` delegates to `victory_shader::emit::translation_fingerprint()`,
which includes `lower::host_max_wave()`, along with `view_heap_limit()`, the `victory-shader` source
hash, build flags, and translator switches, and is evaluated on every lookup. Changes to these
inputs, including switching to a GPU with a different maximum wave width, invalidate old entries.
A simple executable rebuild without translator, `shader_cache.rs`, profile/features, or switch
changes does not invalidate the cache, unless `VICTORY_SHADER_CACHE_KEY=exe` is used.

## 6. How to check that the cache is working

Check logs **separately for each layer**:

### Layer 1: DXIL translation cache (`cache_dir\shaders`)

| Log line (level) | Fields | Meaning and interpretation |
|---|---|---|
| `shaders from the cache and translated so far` (`INFO`, at power-of-two frames from frame 256: `256`, `512`, `1024`, ...) | `hits`, `misses` | Cumulative counters since startup (`crates/victory-gpu/src/queue.rs` / `shader_cache.rs`). `hits` = translations read from disk; `misses` = shaders translated on demand, including unreadable entries translated again. After `warm`, `hits` should dominate and `misses` should be near zero |
| `host wave lanes` (`INFO`, when creating the device) | `min`, `max` | Minimum and maximum GPU wave width (`crates/victory-gpu/src/host.rs`); `max` enters the key as `host_max_wave()` |
| `host view heaps hold <views> views; ...` (`INFO`, when probing the heap) | `views` | Probed view-heap capacity (`crates/victory-gpu/src/descriptor/host.rs`); `views - 1` enters the key as `view_heap_limit()` |
| `shader translated` (`INFO`, once per distinct shader per run) | `stage`, `hash`, `user_data`, `samplers` | **Does not indicate a cache miss.** Logged in `crates/victory-gpu/src/pipeline.rs` when `host_shader()` returns the translated shader, whether from a **disk-cache hit** or **on-demand translation after a miss**. Many `shader translated` lines after `warm` are normal |
| `shader from the cache` / `shader translated and cached` / `unreadable shader cache entry; translating again` (`DEBUG`, per shader) | `path` | Distinguishes individual hits, stored misses, and corrupt entries (`crates/victory-gpu/src/shader_cache.rs`). Requires `--features diagnostics`, for example `VICTORY_LOG=victory_gpu::shader_cache=debug,info`, because standard release builds cap logging at `INFO`. Remember that a diagnostics build uses its own key |

Before starting the game, running `victory warm` a second time confirms DXIL cache reuse in the
terminal summary (`0 translated now`, with almost everything `already cached`).

If `misses` remains high in `shaders from the cache and translated so far` after `warm`, the likely
causes are:
1. `warm` used a different translator (`crates/victory-shader/src/` or `shader_cache.rs`),
   build profile/features (`debug` versus `release`, with/without `diagnostics`), translator-read
   `VICTORY_*` variables, `cache_dir`, GPU (`host_max_wave` / `view_heap_limit`), or executable with
   `VICTORY_SHADER_CACHE_KEY=exe` enabled.
2. The game loads those shaders elsewhere, such as memory or a compressed file the scanner does
   not open.
3. The game supplies a `size` different from the container size.

### Layer 2: driver PSO library (`cache_dir\pipelines`)

| Log line (level) | Fields | Meaning and interpretation |
|---|---|---|
| `host pipeline library loaded` (`INFO`, when opening `host-pipelines.bin`) | `bytes`, `mapped` | Confirms that the driver accepted the saved library (`bytes` = file size; `mapped` = memory-mapped through `MapViewOfFile`). Without a previous library, logs `no host pipeline library yet; starting an empty one`; after a driver/GPU change or file rejection, logs `host pipeline library rejected; starting an empty one` (`error`) |
| `title pipelines to start early` (`INFO`, when reading `early-pipelines.txt`) | `pipelines` | Number of pipeline keys from previous runs loaded for early startup when created |
| `host pipelines all made` (`INFO`, when workers drain a batch with a peak of `>= 10`) | `made`, `loaded`, `started_early` | Cumulative run counters (`crates/victory-gpu/src/pipeline/make.rs`): `made` = PSOs compiled by the driver now (library miss); `loaded` = PSOs loaded from `host-pipelines.bin` (hit); `started_early` = pipelines queued early through `early-pipelines.txt` |
| `host pipeline library saved` (`INFO`, roughly every 20 seconds when changed and at shutdown) | `bytes`, `early`, `made`, `loaded`, `started_early` | In addition to cumulative counters (`made`, `loaded`, `started_early`), reports serialized `host-pipelines.bin` bytes (`0` when no new PSO was added and only `early-pipelines.txt` changed) and `early` (total keys in the early list) |
| `host pipeline cache totals` (`INFO`, after offline warming) | `made`, `loaded` | Reports driver compilation versus actual PSO loads even when the unchanged library needs no save |

After warming, even the first gameplay run can load the saved compute PSOs.
Graphics PSOs are still compiled from encountered draw state. A second warm-up
with the same GPU/driver and settings should log `host pipeline library loaded`,
`made=0` and a nonzero `loaded` count when every compute shader was already warmed.
`early-pipelines.txt` remains the list collected during gameplay, not a list of
speculative pipelines added by the warmer.

## Testing on Windows

```powershell
# 1. Build and run tests
cargo build --release -p victory --features diagnostics
cargo test --workspace
cargo clippy --workspace --all-targets -- -D warnings

# 2. Optional isolated test cache, outside the checkout; do not delete live caches.
# Keep this override for both warming and playing when comparing results.
$env:VICTORY_SHADER_CACHE_DIR = 'D:\victory-data\warm-test\shaders'

# 3. Warm twice: the second run should reuse translations AND compute PSOs.
.\target\release\victory.exe warm <game_dir> --jobs 4
.\target\release\victory.exe warm <game_dir> --jobs 4

# 4. Play and inspect logs from frame 256 (DXIL layer) and pipeline loads (PSO layer).
.\target\release\victory.exe run <game_dir>\<executable> --execute
#    DXIL cache: look for "shaders from the cache and translated so far" hits=... misses=...
#    PSO cache: look for "host pipeline library loaded" and
#    "host pipelines all made" / "host pipeline library saved" (loaded=..., made=..., started_early=...)
```

**The test passes if:** the second `warm` run translates ~0 shaders, and during gameplay `misses`
is a small fraction of `hits` in `shaders from the cache and translated so far`, regardless of
`shader translated` lines. Compare against an empty-cache run without `warm`, where `misses` is
high. A second warm-up with `loaded > 0` and `made=0` confirms compute PSO reuse.
Check the prior `early-pipelines.txt` contents remain intact after offline warming.
